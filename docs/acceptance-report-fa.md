# گزارش پذیرش StoreX / Baharan

تاریخ بررسی: ۲۰۲۶/۱۰/۱۲ — PR شمارهٔ ۷۶، شاخهٔ `feat/attendance-calendar-automation-v1`.

## ۱. نتیجهٔ اجرایی

قرارداد جدید ارسال مستقیم پیاده‌سازی شده است: PDF خصوصی بدون تغییر محتوای A5
با multipart و متد sendDocument بات موجود به گیرندهٔ خصوصی تنظیم‌شده ارسال
می‌شود. رسید، مقصد ثابت، زمان معتبر و موعد حذف ثبت می‌شوند. همان worker قفل‌شده
حذف را با deleteMessage در/پس از ۲۴ ساعت تلاش می‌کند؛ Nextcloud/Talk وابستگی
این چرخه نیستند. قالب، حضور، رزرو، مهمان و تقویم حفظ شده‌اند.

چرخهٔ حذف، retry، نتیجهٔ نامشخص، تأخیر، هشدار پیش از ۴۸ ساعت و شکست نهایی
صریح است. Talk به‌صورت پیش‌فرض خاموش و برای راه‌اندازی آینده آماده است.
راهنمای مستقل فارسی، ابزار پذیرش، پنل وضعیت و حالت cleanup-only برای rollback
اضافه شده‌اند. این متن جایگزین قرارداد قبلی ارسال لینک عمومی برای گزارش‌های
جدید است؛ شواهد تاریخی CI فقط تاریخچه‌اند. نتیجهٔ CI همین تغییرات باید جداگانه
در بخش شواهد ثبت شود؛ Mock اثبات ارسال/حذف واقعی نیست.

هیچ تغییر main، merge، استقرار Production یا ارسال واقعی انجام نشده است.
کلید و محیط شرکت و رضایت گیرندهٔ اصلی در اختیار این محیط نیست.

## ۵. Reporter و وضعیت ارتباطات

همهٔ زمان‌ها تهران هستند: ۰۹:۲۰ و ۰۹:۲۵ یادآوری، ۰۹:۳۰ گزارش، ۰۹:۴۰ و
۰۹:۵۰ بازیابی و ۱۰:۰۰ بازیابی نهایی/هشدار. تاریخ گزارش اولین روز کاری بعدی
است. آخرین داده‌ها پیش از snapshot خوانده می‌شوند؛ لینک یادآوری به مسیر
احرازشدهٔ Reporter می‌رود. پاسخ دوطرفهٔ بله ادعا نشده است.

گزارش‌های جدید در Nextcloud upload/share نمی‌شوند و لینک عمومی ندارند.
فایل با SHA-256 در spool خصوصی نگهداری می‌شود و فقط بایت‌های همان فایل به بله
می‌روند. سقف محافظه‌کارانه ۵۰٬۰۰۰٬۰۰۰ بایت است. نام فایل، MIME، امضا، پایان PDF
و hash پیش از ارسال بررسی می‌شوند. getMe بات موجود و getChat مقصد خصوصی را
تأیید می‌کنند. شناسهٔ حساب تست قبلی به‌عنوان گیرندهٔ اصلی فرض نشده است.

API Message.date معتبر مبنای sentAt است؛ در نبود آن زمان دریافت موفق پاسخ
استفاده می‌شود. موعد حذف دقیقاً sentAt + ۲۴ ساعت است؛ deadline به‌صورت محافظه‌کارانه
از زمان زودترِ ارسال/intent + ۴۸ ساعت تعیین می‌شود. حذف در اولین tick واجد شرایط
تلاش می‌شود، با تعطیلی یا Reporter/Talk خاموش متوقف نمی‌شود. API تنها نتیجهٔ true
را موفقیت می‌داند. not-found و forbidden به‌جای موفقیت، بررسی دستی می‌خواهند؛
نتیجهٔ نامطمئن برای همان IDs قابل تلاش مجدد است. بیش از ۴۸ ساعت WINDOW_EXPIRED
ثبت می‌شود. کپی دانلودشده/forward/screenshot با حذف پیام از بین نمی‌رود.

status موفق تحویل پس از حذف حفظ می‌شود؛ ارسال مجدد مجاز نمی‌شود. شکست ثبت رسید
sendDocument، intent را نامشخص نگه می‌دارد. مدیر باید چت واقعی را بررسی و message ID
و زمان دارای timezone را ثبت کند یا عدم ارسال را صریحاً تأیید کند. بررسی تحت
همان قفل worker انجام می‌شود. shareهای تاریخی و probeهای قدیمی با مسیر مستقل
و اطلاعات اصلی Nextcloud پاک‌سازی می‌شوند؛ داده‌های تاریخی حذف نشده‌اند.

| شاهد واقعی | وضعیت |
| --- | --- |
| پیام متنی بله در workstation قبلی | تأیید قبلی مالک؛ شاهد sendDocument/deleteMessage نیست |
| دریافت PDF توسط گیرندهٔ اصلی متفاوت | **Live Acceptance Pending** |
| deleteMessage و حذف قابل مشاهده پس از سررسید | **Live Acceptance Pending** |
| schedule واقعی و بازیابی قطعی worker | نیازمند staging و مانیتور سازمان |
| دریافت Talk در گروه فنی شرکت | اختیاری؛ Pending تا راه‌اندازی آینده |
| لغو share تاریخی در سازمان | فقط اگر share قبلی موجود است؛ دسترسی اصلی باید حفظ شود |

## ۶. امنیت و آزمون‌ها

آزمون‌های جدید شامل ارسال معتبر و نامعتبر، محدودیت حجم، hash و traversal، چت
اشتباه/گروهی، token/429/timeout، رسید نامشخص، ثبت موفق و شکست DB، مرزهای حذف،
بازیابی restart، حالت disabled/holiday، هشدار داخلی و Deadline، حفظ داده تاریخی
و قراردادهای Talk هستند. APIهای بله/Talk در این مجموعه Mock معتبر دارند؛ TLS و
مهاجرت/قفل PostgreSQL شواهد جداگانه‌اند. رگرسیون مرورگر همهٔ امکانات قبلی و
پنل Talk/فعال‌سازی Reporter بدون Nextcloud را بررسی می‌کند؛ PDFها مصنوعی‌اند.
نتیجهٔ آخرین اجرای این مرحله در verification-report و PR ثبت خواهد شد؛ موفقیت
commit قدیمی جایگزین head جدید نیست. CI قدیمی ۱۴۰۵/۰۷/۱۸ صرفاً شاهد تاریخی است.

مجوز server action/route، کنترل cross-user، صحت فایل، محدودیت مقصد HTTPS، DNS
pinning، گواهی TLS، حذف اسرار از خطا و حفظ snapshot بازبینی شده‌اند. مهاجرت‌ها
افزایشی هستند و جدول هفتگی/تاریخچه حذف نشده است. قالب‌ها و داده‌های آزمایشی
از production جدا هستند؛ ارسال واقعی در CI وجود ندارد.

## ۷. تحویل عملیاتی

DevOps برای Reporter مستقیم باید PostgreSQL، Node/Chromium/فونت، spool پایدار
با پوشه 0700 و فایل 0600، ENV محافظت‌شدهٔ بات موجود، HTTPS egress، NTP و timer
یک‌دقیقه‌ای و مانیتور مستقل heartbeat/حذف را فراهم کند. گیرندهٔ اصلی باید
بات موجود را start، chat_id خصوصی خود را از مسیر مجاز تأیید و رضایت آزمون PDF
و حذف را اعلام کند. شناسهٔ مقصد در UI ذخیره می‌شود؛ Secret فقط در ENV است.

برای Talk آینده، مسئول شبکه URL/نسخه/TLS، حساب اختصاصی، App Password امن،
Conversation Token گروه خصوصی و اعضای پاسخ‌گو را طبق
[راهنمای فارسی مستقل](nextcloud-talk-technical-alerts-setup-fa.md) آماده می‌کند.
Public Sharing لازم نیست. Nextcloud برای بایگانی اختیاری تقویم یا share تاریخی
جداست. هیچ اطلاعات واقعی سازمان اختراع نشده است.

[راهنمای بهره‌برداری](automation-runbook.md) شامل مهاجرت افزایشی
`20261012070000_bale_document_delivery`، health-check، backup/restore و rollback
است. مدل جدید ایجاد نشده؛ ReportDelivery/Config/Alert با فیلدهای چرخهٔ جدید
و دو enum ReportDeliveryKind/BaleDeletionStatus توسعه یافته‌اند. نام و دلیل
فایل‌های تغییرکرده از commitها و ماتریس قابل پیگیری است. در rollback وب، worker
این نسخه با --cleanup-only حفظ می‌شود؛ کار حذف معوق رها نمی‌شود.
